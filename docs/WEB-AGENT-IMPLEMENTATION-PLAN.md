# GPA：本地网页 + Agent 脚本 + Skill 实施计划

日期：2026-09-06  
状态：供 Cursor 实施的产品与技术方案；本次仅规划，没有开始改造产品。  
项目：`/home/zheng/gpt-account`

## 1. 最终决定

把 GPA 做成一个**双击打开的本地账号管理网页**，同时交付**一个只输出 JSON 的 Python 脚本**和**一个专门操作 GPA 的 Skill**。

人类的日常流程：

> 双击「GPA 账号管理」→ 看到账号 → 点击「切换」→ 必要时确认重启 → 页面明确显示结果。

Agent 的日常流程：

> 读取 Skill → 用脚本查账号和目标 → 预览 → 执行 → 按操作编号核验结果。

三者共享一个 Go 后台和一个账号库。网页不操作文件，脚本不复制凭据，Skill 不自己拼 PowerShell 换号命令。

这里的“纯脚本工具”指可阅读、可直接运行、无第三方 Python 依赖的机器客户端，不是把账号切换核心再用 Python 重写一遍。没有服务运行时，脚本负责启动已安装的后台。用户不需要学习任何 GPA CLI 命令。

### 交付物

| 交付物 | 使用者 | 入口 |
|---|---|---|
| `GPA Manager.exe` + 内嵌网页 | 人类 | 解压后双击；可创建开始菜单快捷方式 |
| `gpa_agent.py` | Agent | Python 3 运行，固定 JSON 协议 |
| `gpa-account-manager/SKILL.md` | Agent | 自动识别 GPA 本地账号管理任务，也可显式调用 |
| 迁移和测试文档 | 实现者 | 可重复的隔离验收流程 |

### 本轮范围

必须：本机 Windows App / Windows CLI / 已登记 WSL 客户端；账号导入、添加、更新授权、改名、归档、切换、状态、最近操作、诊断；网页与 Agent 使用同一操作记录。

延后：VPS 部署、跨机器接力、远程公开访问、多人账号系统、云端同步、配额监控、自动挑选订阅、会话迁移。不要把这些做成灰色占位按钮。

不再迭代交互式终端菜单。已有 CLI 在迁移期保留，完成验收后从面向用户的文档和快捷方式中移除。旧脚本和旧账号库不会在本次迁移中自动删除。

## 2. 简单到什么程度

### 三项体验指标

1. 第一次打开：如果已经有可用账号库，直接显示账号；有多个不同来源时才显示一次导入预览。
2. 平时换号：通常一次点击；确实需要重启 App 时两次点击。没有必要时不弹“确定吗”。
3. 整个流程不要求人类输入命令、路径、operation ID、端口或 JSON。

默认以 Windows 桌面端为主要入口。安装了 WSL 不代表用户每次都想更新全部发行版。

首页默认目标为「桌面端」，必要时标注「同时影响 Windows CLI」。用户主动选择过其他目标后，记住选择；目标消失时要求重新选，不悄悄回退到“全部”。

### 明确的产品措辞

- 「当前凭据」表示磁盘身份；「应用已启动」表示进程状态。
- 不能仅凭文件写入就显示「账号已在线验证」或「一定可以发送消息」。
- 正常结果写「已切换本地凭据」；发生重启且已验证进程出现时，加「应用已重新打开」。
- 客户端任务是否空闲无法可靠判断时写「应用正在运行，无法确认任务是否结束」，不要装作已等待空闲。
- 初次授权成功后的日常切换不需要重复登录；凭据被撤销或失效时提供「更新授权」。不承诺永久只授权一次。

## 3. 网页布局与视觉规格

### 3.1 只做一个主页面

不做大型后台侧边栏。主页面负责账号和切换；添加、账号详情、最近操作、设置使用对话框或侧面抽屉。桌面主内容最大宽度约 960px；小窗口时自然变成单列。

```text
GPA 账号管理                         最近操作    设置

切换到哪里  [ 桌面端 ▾ ]                    服务已连接
Windows App 和 Windows CLI 共用登录，会一起更新

你的账号                                      ＋添加账号

● 日常账号       Plus       p***@example.com     当前凭据
  工作账号 A     Business   a***@example.com     [切换]  ⋯
  工作账号 B     Business   b***@example.com     [切换]  ⋯

已切换到工作账号 A · 应用已重新打开          查看详情
```

- 默认浅色、白底、少量灰色分隔线、一个主色。
- 以文字和间距组织页面，不用大面积渐变、玻璃效果、巨大统计卡片。
- 当前账号明确标记，不能只靠颜色。
- 一个账号只露出一个主要动作：切换；辅助动作放 `⋯`。
- 初版先用列表，不做卡片/表格模式切换、拖动排序和复杂筛选。账号超过 8 个才出现搜索框。
- 行高约 68–76px；主要按钮至少 40px 高；正文 14–16px；名称比套餐和邮箱更醒目。
- 邮箱默认部分隐藏，详情可查看完整邮箱；前端数据不会包含任何 token。
- 所有按钮可键盘访问，焦点清晰；对话框关闭后回到原按钮；状态变化使用可访问的 live region。
- 不用颜色表达唯一状态，不把一整行设成不明确的切换按钮。

### 3.2 目标选择

选项是后台发现并登记的目标组：

- 桌面端：App + 与它共用认证文件的 Windows CLI。
- Ubuntu / Debian 等具体 WSL 发行版。
- 本机全部：必须用户显式选择，显示具体成员。

同一个认证文件只能属于一个实际写入单元。用户选择一个逻辑客户端时，后台扩展所有共享该文件的客户端，并把影响范围返回给前端。

选择“本机全部”后，如果不同客户端当前使用不同账号，不出现虚假的全局“当前账号”；显示「各客户端使用不同账号」，账号行显示使用位置。

首页的“当前凭据”随所选范围变化，不以旧 `state.current` 的单个值代替真实状态。

### 3.3 状态和反馈

| 情况 | 页面表现 | 可以做什么 |
|---|---|---|
| 空账号库 | 一句说明 + 导入已有账号 / 添加账号 | 导入或登录 |
| 正在读取 | 稳定骨架，不弹错误 | 等待 |
| 服务暂时断开 | 顶部固定提示，账号保留为缓存并标注过期 | 重试连接 |
| 正在切换 | 当前行显示进度，其他切换按钮暂时禁用 | 查看进度 |
| 需要重启 App | 短确认框，列账号与范围 | 重启并切换 / 取消 |
| CLI 正在使用 | 清楚说明哪个 CLI 需要关闭 | 我已关闭，重试 / 稍后 |
| 进程查询失败 | 明确“无法确认运行状态” | 查看诊断 / 重试 |
| 凭据版本冲突 | 说明冲突来源，禁止用重启确认绕过 | 查看详情 / 更新授权 |
| 写入失败且已恢复 | 显示失败原因和恢复结果 | 重试 |
| 恢复也失败 | 固定告警，显示受影响客户端 | 查看恢复信息 |
| 操作完成 | 页内结果条 + 状态刷新 | 查看详情 |

关键结果不只放在几秒钟就消失的 toast 中。

## 4. 逐条用户流程

### 4.1 打开和关闭

1. 用户解压 Windows 包，双击 `GPA Manager.exe`。
2. 程序检查当前用户、当前账号库是否已有后台实例。
3. 已有实例：验证服务身份后打开同一后台网页；不启动第二个写入者。
4. 没有实例：启动普通用户权限后台，再打开默认浏览器。
5. 关闭网页不会停止正在执行的登录或切换；重新打开仍能看到原操作。
6. 设置里可以“创建开始菜单快捷方式”；开机启动默认关闭。
7. “退出后台”只有无执行中操作时才能立即退出；不能退出时说明正在做什么。

不要求安装 Python、Node、Go、WSL 来打开 Windows 网页。浏览器的本地书签在后台已运行时可使用；后台关闭后应通过快捷方式重新打开。

首次安装没有 Codex CLI 时，仍能查看/导入已有账号。需要添加账号时显示缺失依赖的具体安装说明，不把“登录不了”当成整个网页无法启动。

### 4.2 导入已有账号

- 如果标准账号库已经存在，直接读取；升级 schema 前备份元数据，不重新导入自己。
- 检测旧 Python/旧脚本账号库，显示来源和待导入账号数量。仅检测不修改原库。
- 导入预览分为：新账号、同一身份可合并、需要选择的冲突。
- 用用户身份 + workspace 身份区分席位；同 workspace 的 biz1/biz2 必须保持两条。
- 同身份不同凭据不能按遍历顺序覆盖。只有能可靠比较的新版本才可以采用，否则保留来源并要求处理冲突。
- 未导入的 live 身份可通过“保存当前登录”显式保存；读状态不会偷偷收回刷新凭据。
- 导入结束显示「新增 3 个，跳过 0 个，冲突 0 个」并立即回到账号列表。
- 导入不会切换任何客户端，也不删除旧库。

### 4.3 添加账号

1. 点击「添加账号」。仅需可选备注名；不要求先想一个合法文件夹名。
2. 点击「开始登录」，后台启动隔离的 Codex 官方登录子进程。
3. 页面显示验证网址、设备码、复制按钮和「打开登录页面」。用户在浏览器自行完成官方授权。
4. 后台读取结构化登录事件，页面轮询进度。原始 stdout 不直接暴露给网页。
5. 登录完成后，页面显示邮箱、套餐、备注名；用户可修改备注。
6. 新身份保存为新账号；已有身份更新原账号授权并显示「已更新授权」，不创建重复账号。
7. 如果“更新授权”入口最终登录成另一个人，显示身份不匹配；不替换原账号，允许另存为新账号。
8. 完成后返回主列表；默认不切换。提供可选「保存并使用」且仍走正常切换检查。

取消只停止该登录子进程树；登录超时或后台重启后显示过期/中断，可重新开始。不终止其他 Codex 进程，不写真实 live 认证目录。

设备码、临时授权网址属于短期信息，不写普通操作日志，不通过诊断导出。

### 4.4 切换账号

点击“切换”后先生成后端预览，前端不自行判断是否可执行。

- 无阻塞：立即提交执行，不再加通用确认框。
- App 正在运行：展示「重启并切换到工作账号 A」，列出实际影响范围；确认后只授权本次 App 重启。
- 未托管 CLI 正在运行：提示具体目标，等待用户关闭后重试。不能把 `force` 当作直接覆盖运行中 CLI 凭据的通行证。
- 进程查询失败或进程是否存在未知：阻止写入，允许重新探测。查询成功且确认 App 存在、只是任务是否空闲未知时，仍可由人类确认重启。两种“未知”必须在数据模型中分开。
- 在预览与确认之间账号、目标或进程状态变化：执行前重验；影响范围扩大时必须返回更新后的预览，不能复用旧确认。
- 切换已配置为相同身份时：返回无需切换；同身份有凭据版本冲突仍要处理，不能以身份相同忽略冲突。

“不打断当前 Agent 会话”的具体规则见第 8 节。

### 4.5 改名、更新授权、归档

账号 `⋯` 菜单只有：查看详情、修改备注、更新授权、归档。

- 备注名与稳定账号 ID 分离。改备注不重命名凭据目录，不改变操作引用。
- 归档只隐藏账号，提供归档列表和恢复。若 live 客户端仍使用该账号，标注仍在使用。
- 初版不提供永久删除 token、导出 token、复制 token 的入口；日常管理不需要它们。
- 账号详情展示使用位置、授权保存时间、最近一次本地切换结果。没有证据时不显示“有效/额度正常”。

### 4.6 最近操作和诊断

最近操作默认显示 20 条；每条展示账号、目标、时间、结果。展开后才能看到步骤和路径。

诊断展示：后台版本、连接状态、客户端探测结果、认证文件可读/可写检查结果、冲突概况、最近错误。提供脱敏报告复制功能，不包含 token、完整 auth.json 或登录子进程原始输出。

## 5. 技术架构与复用边界

```text
默认浏览器                         Agent + Skill
    │                                  │
本地 HTTP API                    gpa_agent.py
    │                         HTTP / Windows stdio bridge
    └──────────────┬───────────────────┘
             Go 应用服务层
     Accounts / Login / Switch / Operations
                     │
           账号库 + 操作日志 + 锁
                     │
          Windows / WSL / Linux 适配器
```

### 5.1 选型

- 后台继续使用现有 Go 工程，HTTP 服务优先 Go 标准库。
- 前端初版使用静态 HTML、CSS、原生 JavaScript ES modules；页面规模小，不引入 SSR、Node 常驻服务、复杂路由和全局状态框架。
- 静态文件使用 Go `embed` 打包，产物自包含；开发与生产使用同源 API，减少代理和跨域差异。
- Python Agent 脚本仅使用标准库；参数用 `argparse`，JSON 请求使用 `json`，HTTP 使用 `urllib`，进程使用参数数组。
- 第一版用短轮询更新操作，暂不引入 WebSocket/SSE。仅有进行中操作时约 1 秒轮询；空闲页低频刷新，后台标签进一步降频。
- 元数据和操作日志继续使用文件持久化，不为本轮功能引入数据库。须增加版本号、原子写和恢复日志。
- 新依赖如确实需要，由 Cursor说明用途、锁定版本并验收；本计划不依赖“最新版本”的假设。

### 5.2 建议目录

```text
cmd/gpa-manager/             双击启动 / 后台 / 内部 Agent bridge
internal/app/               面向网页和脚本的用例层
internal/httpapi/           DTO、鉴权、参数校验、路由
internal/operations/        持久化状态机、幂等、恢复
internal/platform/         进程、文件、浏览器、WSL 适配器
internal/gpa/              现有核心，分阶段迁移，不整库重写
web/                       index.html、styles.css、app.js、components/
agent/gpa_agent.py          唯一脚本源码
skills/gpa-account-manager/
  SKILL.md
  scripts/gpa_agent.py      发布时从 agent/ 复制，禁止人工维护两份
  references/protocol.md
scripts/test-web/           隔离 fixture 与端到端测试
scripts/package-web.*      Windows 包、脚本、skill 打包
```

旧 `cmd/gpa` 可短期保留兼容，但必须调用同一用例层；不允许其绕过新操作锁与恢复协议。无法兼容时明确停用旧写入命令并引导打开网页，不能让两套写入逻辑并存。

### 5.3 当前代码可用与必须调整的部分

| 当前文件/能力 | 处理方式 |
|---|---|
| `auth.go` 身份识别、同 workspace 不同席位 | 复用并保留测试 |
| `store.go` 账号库、元数据 | 增加稳定 ID、display_name、archived、schema_version |
| `switch.go` 写入和回滚 | 提取预览/执行，重启授权与凭据冲突分开处理 |
| `ops.go` 操作记录 | 统一状态，不再混用 applied/completed；增加幂等和恢复 |
| `login.go` 隔离登录 | 重构成异步任务；替换直接绑定 stdin/stdout 的方式 |
| `process.go` 进程探测 | 返回明确 none/running/unknown 和原因；通过注入测试 |
| `clientio.go` WSL 适配器 | 统一指定发行版执行；修复直接覆盖文件的写入路径 |
| `ui.go` 终端菜单 | 停止增加功能，迁移后不作为产品入口 |
| 旧 Python `src/gpa` | 迁移参考，禁止继续作为另一套生产核心 |

当前跨发行版 `wslWriteFile()` 使用直接 `cat > 文件`，不是完整原子写；要在目标目录创建受限临时文件，再在同一文件系统内原子替换。不能只因为本地 `atomicWrite()` 已存在就认为所有平台路径都覆盖了。

`parentLooksLikeApp()` 依赖本进程父链；服务常驻后，后台的父进程不是请求它的 Agent，因此不能原样沿用做“不会自杀”的依据。

## 6. 服务启动、连接和数据边界

### 6.1 Windows 是本机服务的主要运行位置

Windows + WSL 环境只运行一个 Windows 后台，由它管理本机桌面端及登记的 WSL 目标。纯 Linux 后台保留可编译能力，但本轮首先验收 Windows + 当前 WSL。

服务以当前普通用户运行。Windows 账号库沿用 `%LOCALAPPDATA%\gpa`，纯 Linux 沿用用户数据目录；不自动移动会话文件。

### 6.2 本地网页连接

- 只监听 `127.0.0.1`，不绑定 `0.0.0.0`，不为 WSL 客户端扩大监听范围。
- 从一个默认端口开始尝试；被占用则选择空闲端口，由启动器自动打开正确地址。用户不用输入端口。
- 账号库下记录受限的 runtime 信息：版本、服务实例 ID、实际端口、进程 ID和已安装程序路径。PID 存在本身不足以证明是 GPA。
- 实例单例按账号库绑定；再起实例时通过握手核验，而不是盲目信任端口或终止同 PID 进程。
- 服务断开后，网页显示连接提示，不重复发送最后一次写入操作。

### 6.3 本地网页也要有最小访问边界

账号管理服务不能仅凭“来自 localhost”就接受切换请求，因为其他网页也可能向本地端口发送请求。

- 首次打开网页由启动器生成短时、一次性 bootstrap 凭据，通过 URL fragment 交给页面，兑换 HttpOnly、SameSite=Strict 的本地会话 Cookie 后立即清掉 fragment。
- bootstrap 值不放 query、不进入日志，不作为长期密钥；响应设置 `Cache-Control: no-store`。
- 写 API 检查精确 Origin、Host、会话与 CSRF 凭据；不提供宽松 CORS。
- 网页和 API 同源；只允许必要脚本来源，防止账号备注通过 HTML 注入脚本。
- HTTP API 不接受任意文件路径、任意命令或任意外部 URL 作为执行目标。
- 原始认证资料永远留在服务端。API DTO 用显式字段构造，不能序列化整个 `Account.Auth`。
- Agent 使用独立的本地能力凭据，保存在当前用户可读文件；不能因为请求 JSON 写着 `actor=ui` 就获得人类确认权限。
- 本方案防止无关网页驱动本地服务；不声称可以防御已完全控制同一操作系统用户的恶意程序。

### 6.4 WSL Agent 连接 Windows 后台

不要假设所有 WSL 网络模式都能访问 Windows 的 `127.0.0.1`。

- Windows Python 和纯 Linux Python：直接连接同机 loopback API。
- WSL Python：调用已安装 Windows 程序的内部 `--agent-stdio` 通道，JSON 通过 stdin/stdout 传递；Windows bridge 在 Windows 内访问 loopback 服务。
- bridge 是内部传输适配，不是保留原来的人工 `gpa use` 命令，也不重写业务逻辑。
- 每次 bridge 请求一个完整 JSON 消息和一个 JSON 响应；stdout 不混入 banner，stderr 只放脱敏错误。
- 调用 Windows 可执行文件采用 `subprocess` 参数数组，不拼用户输入到 PowerShell 或 shell 命令。
- WSL interop 不可用时返回 `TRANSPORT_UNAVAILABLE` 和处理提示；不能偷偷新建第二个 WSL 服务写同一个账号库。
- 服务尚未启动时，脚本/bridge启动已配置的可信程序进入后台模式，不自动打开浏览器；等待有界健康检查。

## 7. 数据模型与操作协议

### 7.1 账号、目标和校验结果

账号至少包括：

```json
{
  "id": "acct_01...",
  "display_name": "工作账号 A",
  "legacy_aliases": ["biz1"],
  "email_hint": "a***@example.com",
  "plan": "business",
  "archived": false,
  "credential_revision": 4,
  "configured_on": ["desktop"],
  "verification": {"local_credentials": "matched", "online": "not_checked"}
}
```

目标 ID 必须来自发现结果，UI 显示标签与内部 ID 分开。目标记录存储关系、平台、已登记发行版、可用性和最近探测时间。进程存在性使用 none / running / unknown；任务状态另外使用 idle / busy / unknown。没有可靠信号时任务状态保持 unknown，不能从“进程已找到”推断 idle。

身份、token、路径的内部信息不直接暴露给首页。需要完整邮箱时走受鉴权详情接口；认证内容没有详情接口。

### 7.2 预览与提交

推荐接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/status` | 当前账号、目标、服务状态 |
| `GET /api/v1/accounts` | 活跃账号列表 |
| `PATCH /api/v1/accounts/{id}` | 备注和归档状态 |
| `GET /api/v1/accounts/{id}` | 非敏感详情 |
| `POST /api/v1/imports/preview` | 从已发现来源生成导入预览 |
| `POST /api/v1/imports` | 确认导入，返回操作编号 |
| `POST /api/v1/logins` | 开始独立登录 |
| `GET /api/v1/logins/{id}` | 脱敏登录状态与短期设备码 |
| `POST /api/v1/logins/{id}/cancel` | 取消指定登录 |
| `POST /api/v1/switch-plans` | 检查账号、目标、实际影响和阻塞 |
| `POST /api/v1/operations` | 根据 plan_id 提交切换 |
| `GET /api/v1/operations` | 最近操作 |
| `GET /api/v1/operations/{id}` | 查询结果 |
| `POST /api/v1/operations/{id}/retry` | 同一个操作编号重新检查 |
| `POST /api/v1/operations/{id}/cancel` | 仅取消尚未开始写入的操作 |
| `POST /api/v1/operations/{id}/confirm` | 网页会话确认本次 App 重启 |
| `GET /api/v1/diagnostics` | 脱敏诊断 |

预览包含：`plan_id`、过期时间、稳定 `account_id`、请求范围、实际范围、共享客户端说明、检查结论、阻塞原因、预览版本。

计划绑定凭据 revision、目标集合、影响范围和必要的状态快照。提交时重新探测；计划过期或条件变化返回 `PLAN_STALE`。客户端拿新预览，不能靠一个旧按钮确认更大的范围。

写入请求携带 `idempotency_key`。相同键和相同请求返回同一操作；同键不同请求返回冲突。刷新页面、双击按钮、网络超时重试不会执行两次切换。

解析器拒绝未知 JSON 字段、未知枚举、空 targets、重复/不明确账号引用。不提供缺失范围时自动“全部”的默认值。

### 7.3 状态机

操作主状态统一为：

```text
queued → running → succeeded
   │        ├── waiting_user ──确认/重试──→ running
   │        ├── blocked ───────条件变化后重试──→ running
   │        └── failed
   └── cancelled
```

- `waiting_user`：需要人类重启确认或关闭 CLI；不是后台持续忙跑。
- `blocked`：查询失败、凭据冲突、目标不可达等；不自动解除。
- `phase` 独立表达 checking / stopping_app / collecting_credentials / writing / starting_app / verifying / restoring。
- `failed` 带 `recovery.status`：not_needed / restored / failed。
- `interrupted` 可作为失败原因，不应在重启后把执行中操作直接标成功。
- 登录使用单独状态：starting / waiting_authorization / succeeded / cancelled / expired / failed。
- 操作完成后再次 apply/confirm 返回原结果，绝不执行第二遍。
- 对 failed 的显式 retry 只在恢复已完成或无需恢复时接受：attempt 增加，操作 ID 保持；重新预览与检查。恢复失败先处理恢复，不直接再次写入。retry 请求本身也需幂等键。

业务等待和执行错误不是同一个概念。HTTP `202` 表示已受理；业务结果通过 operation 查询，不能把 HTTP 200 当作账号切换成功。

### 7.4 切换事务与恢复

1. 用短锁检查并创建操作、验证目标身份，持久化意图。
2. 若需要用户操作，持久化 waiting 状态后释放锁；不持锁等待人登录或关闭 CLI。
3. 真正执行时取得跨进程账号库锁并重验计划。
4. 检查所有受影响客户端可达、认证可读、进程状态明确；初版禁止按 `force` 跳过冲突。
5. 必要时按本次确认关闭 App；确认退出后回收刚刷新的凭据。
6. 比较可用凭据版本；有冲突就阻止替换，而不是“Windows 的最后读到所以优先”。
7. 在受限恢复目录保存旧文件和元数据快照，先持久化 journal，再进行逐目标写入。
8. 每个目标在其自己的文件系统中原子替换。成功后更新 journal；全部成功才更新最终元数据。
9. 按计划重开 App，验证文件身份和进程结果。
10. 持久化完整结果后完成操作。

多台本地客户端的多文件写入无法做到真正同时原子提交，应明确这是“带恢复日志的多步事务”。中途出错必须报告哪些写过、哪些恢复了。

恢复时先比较当前文件是否仍是本次操作写入的版本。若客户端已经刷新了新凭据，不能盲目用备份覆盖；转为 recovery failed/needs attention，保留候选供恢复。

后台启动时检查未完成 journal：能安全恢复则恢复，不能确定就标需处理；不自动重放切换、不自动杀进程。回滚后也核对结果，不能吞掉恢复失败。

恢复快照含凭据，必须使用用户私有权限；成功后的快照按明确短期保留策略清理，恢复未完成的快照不能被清理任务删除。

### 7.5 登录实现要点

当前 `LoginAccount()` 直接把输出接到终端，网页不能直接调用后等待 HTTP 请求结束。

- 改为由后台持有子进程，使用 context 和超时，按 operation/login ID 管理生命周期。
- 每次登录唯一隔离目录；名称在任何文件操作前验证。
- 解析设备码和官方验证地址形成事件；不能可靠解析时明确报不支持的输出格式，保留脱敏诊断，不伪造进度。
- 记录已验证的 Codex CLI 版本/输出样例作为适配器测试 fixture；不把输出文案当永久稳定协议。
- 隔离目录采用官方可用的认证缓存存储模式；需验证当前 CLI 是否会写系统 keychain。不得未经验证就假设设置临时 CODEX_HOME 一定不会影响正式登录。
- 登录期间不持账号库全局锁；落库时加锁、复查同身份/槽位冲突。
- 取消时只操作保存的子进程句柄/进程组，不按 `codex` 名字全局 taskkill。

## 8. Agent 脚本的完整契约

### 8.1 常用动作应少而稳定

```bash
python3 gpa_agent.py status
python3 gpa_agent.py accounts
python3 gpa_agent.py preview --account biz1 --target desktop
python3 gpa_agent.py switch --plan-id PLAN_ID --request-id REQUEST_ID
python3 gpa_agent.py operation --id OP_ID
python3 gpa_agent.py wait --id OP_ID --timeout 30
python3 gpa_agent.py retry --id OP_ID
python3 gpa_agent.py open-ui
python3 gpa_agent.py diagnose
```

机器可控管理动作另提供 `import-preview`、`import-apply`、`rename`、`archive`、`unarchive`、`login-start`、`login-status`、`login-cancel`。Skill 只在用户有对应意图时调用。添加账号涉及官方网页授权时交给用户，不模拟认证页面。

`--account biz1` 是兼容别名，解析后必须返回稳定 account_id；匹配多个账号时失败，不能选第一个。明确账号但没说范围时，Skill 可以沿用本次对话已确定范围；否则报告当前可选范围并询问，不自动全部切换。

脚本仅实现参数、发现服务、启动、传输、超时、JSON 校验和退出码；不实现身份识别、凭据优先级或进程停止。

### 8.2 请求和结果

统一封装示例：

```json
{
  "schema_version": 1,
  "request_id": "req_...",
  "status": "waiting_user",
  "operation_id": "op_...",
  "account_id": "acct_...",
  "targets": ["desktop"],
  "reason_code": "APP_RESTART_REQUIRED",
  "message": "桌面应用正在运行，需要在管理页面确认重启。",
  "next_action": {"type": "open_ui", "operation_id": "op_..."},
  "verification": {"local_credentials": "not_checked", "app_process": "not_checked", "online": "not_checked"}
}
```

- stdout 永远只有一个 JSON 文档；没有颜色、进度条、账号表格、浏览器 URL 密钥或堆栈。
- stderr 可以输出短诊断但不能泄露凭据；堆栈只写脱敏开发日志。
- `wait` 到截止时间返回当前真实状态和同一编号；不会在服务端取消或重建操作。
- 读取一次状态不启动登录、不刷新 token、不切换账号。
- 传输超时后，使用原 request_id 查询；只有已确定请求未受理才重新提交。相同键重试也必须幂等。

退出码：

| 码 | 意义 |
|---|---|
| 0 | 查询成功，或操作成功 |
| 1 | 操作失败或恢复失败 |
| 2 | queued / running / waiting_user，尚未完成 |
| 3 | blocked，需要条件改变 |
| 4 | 参数、身份或目标不明确 |
| 5 | 服务/传输不可用 |

`status` / `accounts` 的查询成功用 `status=ok`；操作输出使用第 7 节状态。不要靠退出码单独推断业务状态。

### 8.3 不打断正在处理任务的 Agent

常驻服务无法从自己的父进程判断是谁请求切换。第一版采取简单、可测试的规则：

- Agent 可执行不需重启、无运行中 CLI 的切换。
- Agent 请求需要停止正在运行的 App 时，返回 waiting_user，并给对应网页操作入口；不会直接重启。
- Agent 能创建计划，但不能通过伪造 `actor=ui` 调用网页确认权限。
- 有运行中 CLI 时始终等待用户关闭，不全局杀 CLI。
- 不提供通用 `--force`；网页的“确认重启”仅绑定该操作、账号、范围和版本，不代表允许覆盖未知版本凭据。
- 现有用户授权在会话内可以继续用于合法操作，不重复问没有必要的问题；但不能把“帮我切一下”扩展成清空、登出或重启所有程序。

用户需要立即重启时，通过已经打开的网页明确操作。以后如要让 Agent 完全自主跨重启续跑，应另做独立任务恢复机制，本轮不靠 shell 延时自杀实现。

## 10. 迁移和兼容规则

1. 当前工作区存在大量未提交改动和未跟踪 Go 文件。Cursor 首先查看 git status，保存基线，不 reset/clean、不覆盖已验证修复。

### 12.2 核心与故障

- 凭据新旧冲突；相同时间戳不同刷新令牌；不可比较版本。
- Windows/WSL 认证目录不同、共享文件、两个发行版存在相同 Linux 路径。
- 查询命令失败；发行版离线；App 停止失败/启动失败。
- 第一份/第二份认证写入失败；元数据失败；日志失败；恢复失败。
- 预览后账号或客户端状态变化；确认范围过期。
- 同时两网页/网页+Agent切换；锁争用；后台中途退出后恢复。
- 旧客户端恰好刷新 token 时恢复不覆盖新版本。
- 无效 HTTP 参数、未知脚本参数、未授权 Origin、错误 Host、缺少 CSRF、Agent 伪造网页 actor。
- 确认任何错误输出、诊断导出、前端缓存都没有 token。

### 12.3 Agent 真实调用

- “查看账号”：查询成功，零认证写入。
- “将 Ubuntu 切到 biz2”：解析正确席位和目标，预览、执行、核验。
- “切到工作账号”：有歧义时不猜，不默认全部。
- “App 正在运行时切号”：返回明确等待操作，不结束当前会话。
- “刚刚切换超时，继续”：查询原 request_id/operation_id，不重复切换。
- “添加账号”：启动隔离授权并交给用户，不自动化官方认证界面。
- bridge 不可用：结构化错误，不绕到直接写 auth.json。

### 12.4 测试边界

自动化测试默认采用临时账号库 + 伪造 JWT + 注入的平台适配器，绝不覆盖当前会话凭据或重启当前应用。测试状态与 production 状态隔离；测试伪造能力不通过公开 API 开启。

真实授权、真实 App 重启、真实切号另列人工验收。只有用户安排好可中断窗口后才执行；没有执行就如实标未验证。Windows 交叉编译通过、Windows 原生逻辑测试通过、浏览器流程通过是不同证据，不混为一个“全通过”。
